# 規則更新失敗：自動恢復、說清楚原因、讓使用者自己回報 — 設計文件

- 日期：2026-10-30
- 狀態：待審閱
- 起因：Pack 測試者 Irfan Ege 在 Day 12 回報「Update failed」（只有這兩個字，看不出原因）

## 1. 為什麼要做

Untail 從網站下載規則（`rules.meta.json` + `rules.json`）。失敗時設定頁只顯示一句「Update failed; keeping the current rules.」，使用者和開發者都不知道原因，也沒有管道回報。

2026-10-30 調查（見 memory 與對話）：
- 線上規則本身沒問題：雜湊相符，目前版本和 0.1.1 的檢查邏輯（c490600、acbcefa）都接受。
- 最可能的原因有兩個，無法分辨：
  1. 使用者當下網路有問題
  2. **CDN 快取不一致**：每天排程重新產生規則，`rules.json` 內含每天的 `version`，所以雜湊天天都變；GitHub Pages（Fastly）對兩個檔案各自快取 `max-age=600`。拿到新 meta 配舊 rules 就雜湊不符，`updateRules` 回傳 `failed`，**而且記錄了檢查時間，24 小時內不再重試**。

另外發現一個相關問題：`loadRules`（`apps/mobile/src/lib/rulesStore.ts:43`）只要有下載過的規則就一律用下載的，不管 app 內建的是否比較新。升級 app 後，更新一直失敗的使用者會停在舊規則。

## 2. 目標、非目標、反目標

### 目標
1. 大部分失敗讓 app 自己恢復，使用者什麼都不用做
2. 設定頁說清楚失敗原因，以及 app 接下來會怎麼做
3. 自己恢復不了時，讓使用者能一鍵開啟現有的回報信，附上診斷資訊，由他自己按送出
4. 升級 app 一定能用到內建的較新規則

### 非目標
- 不做任何自動回傳、遙測、當機回報，也不架伺服器
- 不改規則內容本身
- 不新增背景排程；沿用現有的啟動與回到前景時檢查

### 反目標（做到了也算失敗）
- 任何資料在使用者沒按「送出」的情況下離開手機
- 為了會自己好的失敗跳出提示打擾使用者：錯誤只在設定頁顯示，不跳 toast 或對話框
- 隱私權政策和實際行為不一致

## 3. 設計

### 3.1 網站端：規則內容沒變就不換版本（main，獨立先上）

`rules.yml` 每天排程和每次 push 都會重新產生規則。改成：產生後先抓線上的 `rules.json`，比較「除了 `version` 以外的內容」：
- **一樣**：沿用線上的 `rules.json` 和 `rules.meta.json` 原檔放進 site 產出物，版本和雜湊都不變
- **不一樣**，或線上抓不到：照現在的方式用新版本號發佈

這樣只有規則真的變了才會換雜湊，快取不一致的機會從「每天一次」降到「每次真的改規則一次」。

- 比較的方式（如何正規化、放在 `rules/src` 的哪裡、要不要單獨的 script）交給實作者，但必須有測試：內容相同時沿用、只差 version 時沿用、內容不同時換新、線上抓取失敗時換新
- `pnpm test:regression` 和現有的 live 檢查不變
- 這部分不需要改 app，0.1.1／0.1.2 使用者立刻受惠，所以**先在 main 上做並推送**（推送前照慣例請 codex + agy 審查，並用 0.1.1 core 驗證 dist）

### 3.2 App：失敗分類與重試（新版本，見第 5 節）

`updateRules` 的結果從單一個 `failed` 細分成四種原因：

| 原因 | 何時 | 是否記錄檢查時間 | 下次自動重試 |
|---|---|---|---|
| `network` | `fetchText` 丟錯（連不上、非 2xx），或 meta 不是合法 JSON（例如公共 Wi-Fi 的登入頁回傳 HTML） | 否 | 下次啟動或回到前景（同現在） |
| `mismatch` | 下載的 `rules.json` 雜湊和 meta 不符 | 記錄「15 分鐘後可再試」 | 15 分鐘後的下一次啟動或回到前景 |
| `unsupported` | meta 的 `schemaVersion` 不是 1，或下載的規則通不過 `validateBundle`（例如新規則用了這版 app 不認得的類別） | 是（24 小時） | 24 小時後 |
| `invalid` | meta 缺 `sha256`、`rules.json` 不是合法 JSON | 是（24 小時） | 24 小時後 |

- 15 分鐘是**我的判斷**：Fastly 快取 600 秒，15 分鐘足以讓兩個檔案都過期
- `fetchText`（`AppContext.tsx`）目前沒有逾時，卡住的請求永遠不會被歸類。加 15 秒逾時，逾時算 `network`（**我的判斷**）
- 手動按「立即更新規則」照舊無視節流，立刻檢查
- 實作方式（另存 `retryAt`，或把 `checkedAt` 往前推）交給實作者，但要有單元測試涵蓋上表每一列

### 3.3 App：本機記錄最近一次結果

在既有的 kv 表（只在手機上）記錄：
- 最近一次**成功**的時間（`updated` 或 `up-to-date` 都算）
- 最近一次**失敗**：原因、時間、同一原因連續發生的次數
- 成功一次就清除失敗紀錄

自動檢查（啟動、回到前景）的結果也要記錄，不是只有手動按的時候。這些資料不離開手機，不需要另外的同意。

### 3.4 App：設定頁顯示

「規則版本」那一列下方：
- 規則版本後面標出來源：「（已下載）」或「（App 內建）」
- 「上次成功更新：<相對或本地時間>」；從未成功過就不顯示這行
- 有失敗紀錄時，顯示一行具體說明（三種語言都要有）：
  - `network`：目前連不上規則網站，下次打開 App 會再試
  - `mismatch`：下載到的規則不完整，幾分鐘後會自動重試
  - `unsupported`：這個版本的 Untail 讀不懂新規則，請到商店更新 App
  - `invalid`：規則網站回傳的資料有問題，明天會再試
- 手動更新的即時結果（現有的 `settings.update.*`）照舊顯示，文字改成對應上面四種原因

文字是**我的草稿**，三種語言的最終措辭交給實作者，但要短、不用技術名詞、說明 app 接下來會做什麼。

### 3.5 App：回報按鈕

**出現條件（我的判斷）**：同一原因連續失敗 3 次以上，或原因是 `unsupported`／`invalid`（重試也不會好）。

按下後用現有的 `reportMailto` 機制開啟使用者的郵件 app，收件人同「回報問題」（`support@ttylab80387.com`）。信件內容：
- 開頭同現有回報信的隱私提醒（`note`）
- `Rules update: <原因>`
- `Last failure: <ISO 8601 UTC 時間>`，`Failures in a row: <次數>`
- `Last success: <ISO 8601 UTC 時間 或 never>`
- `App <版本> / Rules <使用中版本> (<downloaded|built-in>) / Built-in <內建版本>`
- `<平台> <系統版本>`，例如 `Android 16`（**我的判斷**：分辨網路與系統差異有幫助，且使用者看得到、能刪）

不含連結、不含歷史紀錄、不含任何識別碼。`reportMailto` 目前只接受連結回報的欄位，擴充或另寫一個函式交給實作者，兩者都要有測試。

### 3.6 App：內建規則比下載的新時用內建的

`loadRules` 改成：下載的快取有效，**而且**版本不舊於內建版本，才用下載的；否則用內建的。

- 版本格式固定為 `YYYY.MM.DD.HHMM`（`rules/src/bundle.ts` 的 `makeVersion`），可直接比字串；實作時仍要驗證格式，格式不對就當成較舊
- 內建比較新時要不要刪掉舊快取，交給實作者；不刪也行，下次檢查會因雜湊不同重新下載
- 下載後如果版本比內建還舊，仍用內建的
- 更新成功但內建規則仍比較新時，設定頁照樣顯示成功，版本後面標「（App 內建）」
- 這個比較要成立，內建規則必須是**某一次正式發佈的原檔**，見 3.8

### 3.8 App 內建規則改為下載已發佈的原檔

問題：`makeVersion` 用的是 build 當下的時間。若在本機重新 build 規則再打包進 app，內建版本號一定比網站新，即使內容比較舊（例：`feat/qs-tile` 內建 `2026.10.22.1355`，缺 main 的 Bilibili 修正 048b598、f3fe662）。3.6 會因此一直用內建的，反而用不到網站上已修好的規則。

做法（**我的判斷**，使用者未表示反對）：`apps/mobile/scripts/sync-rules.mjs` 改成從 `SITE_BASE_URL` 下載已發佈的 `rules.json` 與 `rules.meta.json`，驗證雜湊相符、通過 `validateBundle` 後，把 `rules.json` 原檔放進 `apps/mobile/assets/`，不再從本機 `rules/dist` 複製。

- 代價：規則必須先推到 main、網站發佈後，app 才能打包新規則（現在本來就是這個順序）
- 下載或驗證失敗時，script 失敗結束，不覆寫現有檔案
- 發版前的步驟（寫進文件或 script 說明）：先確認 main 的規則已發佈，再跑 `sync-rules`、提交、build

### 3.7 隱私權政策

兩個地方、三種語言都要改：`docs/site/privacy.html`（zh-Hant、en、ja 三段）和 app 內的 `privacy.p6`（三個 locale JSON）。

- 「回報問題」段落：補上從設定頁回報規則更新問題時，信件包含的項目（3.5 的清單），以及這同樣只有在使用者自己按送出時才會寄出
- 補一句：App 會在手機上記錄最近一次規則更新的結果與原因，只用於在設定頁顯示和使用者自己發送的回報信

寫完跑 `scripts/check-invisible.py`（Write／Edit 工具曾把 `\uXXXX` 轉成實際字元）。

**上線時機（我的判斷）**：`docs/site/privacy.html` 一推到 main 就會上線，但 app 端在未合併的分支上。為了不違反反目標，新增的句子寫明「0.1.3 起」，和 3.1 一起先上 main；app 內的 `privacy.p6` 跟著 app 分支走。這樣不論哪一邊先上線，政策都不會跟實際行為不一致。

## 4. 測試

- 單元測試（vitest）：3.1 比較邏輯；3.2 每種原因的分類、是否記錄檢查時間、15 分鐘重試；3.3 成功清除失敗紀錄、連續次數；3.5 信件內容；3.6 版本比較（含格式錯誤）
- 既有的 `pnpm test`、`pnpm typecheck`、`pnpm test:regression` 全綠
- 實機（Xperia 5 II 或 vivo）：
  - 飛航模式按「立即更新規則」→ 顯示 `network` 說明，關掉飛航後回到前景會自動成功並清掉說明
  - 連續失敗 3 次後出現回報按鈕，按下開啟郵件 app，內容正確且可編輯；不按送出就不寄
  - 用較新的內建規則安裝新版 app，蓋過裝置上較舊的下載快取 → 設定頁顯示內建版本與「（App 內建）」
- `sync-rules`：網站正常時放進的檔案和線上 `rules.json` 位元組完全相同；斷網或雜湊不符時失敗且不覆寫
- `mismatch` 很難在實機重現，以單元測試為準

## 5. 範圍與交付

- **3.1 網站端 + `docs/site/privacy.html`**：在 main 上做，審查後推送，不需要發新版 app
- **3.2～3.6、3.8、app 內 `privacy.p6`**：目前 Play 上最新是 0.1.2（versionCode 4），0.1.3（versionCode 5）尚未上傳（使用者 2026-10-30 確認）。所以 app 端跟 0.1.3 一起發：先把 main 合併進 `feat/qs-tile`（拿到 Bilibili 修正與 3.1），再從它開新分支實作，完成後合回 `feat/qs-tile`。versionCode 維持 5
- 實作者決定：比較與正規化方式、kv 欄位名稱、時間顯示格式、回報函式的形狀、三種語言的最終措辭

## 6. 我替使用者做的判斷（請確認）

1. `mismatch` 15 分鐘後重試；`fetchText` 15 秒逾時
2. 回報按鈕的出現條件：同一原因連續 3 次，或 `unsupported`／`invalid`
3. 回報信附上平台與系統版本
4. 內建規則改為下載已發佈的原檔（3.8）
